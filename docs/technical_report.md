## 1. Abstract

SubBill is a local-first agentic application for reviewing recurring charges and personal bills. Its purpose is to make recurring billing review more consistent by combining deterministic transaction analysis with persistent, user-scoped memory and bounded language-model recommendations. It imports CSV statements, preserves each transaction, identifies selected billing anomalies, retrieves prior user decisions and usage evidence, and presents recommendations for explicit human approval. SQLite is the authoritative store. The design deliberately excludes bank connectivity, payment execution, automatic cancellation, and email sending. Cancellation requests are local drafts labelled UNSENT.

The original project supplied a useful SQLite and CSV foundation, but several evaluation components were not genuine: the review orchestrator was ordinary Python rather than LangGraph, the scenario runner marked cases 4–10 PASS without executing them, and ablation/metrics files contained predetermined values. The revised implementation repairs the core persistence and analysis layer, adds a real LangGraph `StateGraph` source implementation, adds a Streamlit frontend, and replaces fabricated evaluation outputs with executed deterministic checks. The current execution environment had no network access and did not contain LangGraph, Streamlit, or Groq; therefore those integrations are declared but not falsely reported as runtime-verified.

## 2. Problem definition and supplied data

Students and young professionals may have subscriptions, utilities, and recurring services spread across monthly statements. The application should distinguish likely recurring merchants from one-off purchases, detect anomalies without losing individual transaction detail, and remember user choices across a full process restart.

The supplied `cycle1.csv`, `cycle2.csv`, and `cycle3.csv` each contain eight familiar merchant rows and one Local cafe transaction. `user_b_cycle1.csv` provides a second-user isolation fixture. The observed sequence includes Netflix at approximately $15.99 in Cycle 1, $20.99 in Cycle 2, and $15.99 plus a separate $20.99 charge in Cycle 3. The Cycle 3 Netflix rows are two separate transactions on March 5 and March 6. The memo contains an instruction-like string asking the assistant to send email; it is untrusted CSV data and must not be executed. The dataset does not independently prove a renewal date change. A Gym post-cancellation charge is demonstrable only after a cancellation decision has been recorded with a date earlier than that charge. The historical demonstration uses a replay timestamp of February 6, 2026 for that explicit decision.

## 3. System architecture

The application has six principal layers. The Streamlit frontend collects CSV uploads, shows dashboard and register information, requests user decisions, and presents cancellation drafts. The Python tools validate and parse CSV rows, normalize known merchant labels, retain transactions, detect duplicates and changes, and write decisions/evidence. SQLite persists the data and provides per-user retrieval. LangGraph coordinates parsing, memory retrieval, and recommendation. The LLM adapter provides either deterministic mock behavior or Groq chat completions. A policy validator constrains model output before it reaches the frontend.

The compiled graph is defined using LangGraph `StateGraph`, `START`, and `END`. Its implemented nodes are `parse_statement`, `load_persistent_memory`, `analyze_and_decide`, and `awaiting_human_approval`, connected by explicit directed edges and a conditional route that returns findings requiring approval to the frontend. The analysis node calls a provider, then validates the action and evidence references. The human approval step is intentionally outside the graph: an agent cannot approve its own recommendation or execute cancellation. The user selects Keep, Cancel, or Review Later and supplies a reason; the application appends that decision to SQLite.

## 4. Persistent memory and data integrity

SQLite is the source of truth. `transactions` stores user ID, billing cycle, SHA-256 source hash, source row reference, date, description, amount, currency, normalized merchant key, and memo. A unique index on user ID, file hash, and row reference prevents duplicate row writes. `source_files` prevents re-ingesting an identical file for the same user. `register_items` stores amount, interval, renewal date, status, version, source reference, creation timestamp, and superseded version link. Corrections create a new register version rather than silently mutating the old row.

`decisions` stores user decision, reason, date, and current/superseded state. `evidence` stores user-provided usage notes. `issues` stores anomaly type, detail, status, resolution, and idempotency key. `drafts` stores cancellation request text with an UNSENT label and idempotency key. `corrections` stores proposals and confirmation state. `action_log` stores tool activity, outcome, memory read/write notes, errors, and timing where recorded. User IDs are included in data retrieval and write operations. The database is reopened by each CLI process and survives process termination; no conversation state is required to restore earlier decisions.

## 5. Detection and agent policy

CSV validation requires date, description, amount, and currency. Dates must parse as ISO dates and amounts must be numeric and nonnegative. Known aliases normalize merchant labels; unknown descriptions are retained as `unknown_...` transactions and reported as unfamiliar merchants, not automatically promoted into recurring subscriptions. This is an important safeguard against treating every purchase as a subscription.

Duplicate detection counts each merchant's charges in a billing cycle while retaining all rows individually. Amount comparison checks the observed amounts against the current register amount with a one-cent tolerance. Renewal-day comparison checks the current cycle's first billing date against the prior cycle's last billing date and flags a shift greater than three calendar days; this is a heuristic and needs provider confirmation. The supplied cycles do not demonstrate a renewal-day shift. Billing after cancellation is flagged only when a recorded cancellation decision predates the charge. All issue writes use idempotency keys.

The LLM can recommend a bounded action such as escalation, requesting usage evidence, keeping, or review later. It cannot modify permissions or call external services. Groq receives issue, register, and evidence context as untrusted data and is required to return JSON. Python validates the action schema and filters references to evidence IDs actually retrieved. The mock provider is deterministic and supports offline evaluation. Neither provider has a cancellation or payment tool.

## 6. User approval and safety

The application presents evidence, issue detail, model rationale, and previous decisions before offering the user three explicit choices: Keep, Cancel, or Review Later. A reason is required by the frontend. The decision is appended and the previous current decision is superseded. The cancellation draft generator is idempotent: repeating the request returns the same draft rather than creating multiple records. Drafts are never sent. There is no bank integration, payment tool, cancellation API, or email sender.

CSV memo content is treated as untrusted input. The supplied injection-like memo is detected and logged; it does not alter the workflow. The agent's prompt also states that transaction fields are data, not instructions. Deterministic validation, access control, and persistence remain in Python.

## 7. Evaluation method and results

Sixteen automated unit tests exercise idempotent ingestion, user isolation, amount changes, duplicate preservation, cancellation-after-decision detection, decision history, draft idempotency, register versioning, untrusted CSV detection, process restart recovery, correction proposals, and renewal-day shift detection. The executed test suite is recorded in `results/test_results.txt`.

The scenario runner creates an isolated temporary database and executes ten checks: initial use, later use, full process restart, approved correction, user isolation, missing/conflicting evidence validation, injected transient failure with retry, untrusted instruction handling, duplicate billing, and cancelled subscription billed again. It writes JSON/CSV/Markdown output from observed results; it no longer fills in PASS values for unexecuted scenarios. The three-cycle demo evidence in `results/` is a separate historical replay using the supplied data and explicit replay timestamps. A dedicated cold-restart check (`python -m subbill.restart_check --out results/restart_check`) also uses two separate Python processes: the first imports Cycles 1–2 and saves usage evidence and decisions, then closes SQLite; the second reopens that same file, imports Cycle 3, and retrieves the saved Netflix decision/evidence while detecting the duplicate Netflix and post-cancellation Gym findings.

The memory ablation executes three paired cases using the same mock provider and issue input while changing only whether register/decision context is supplied. The recorded outcomes show that memory changes the recommendation: cancelled billing escalates with a remembered cancellation decision but requests evidence without it; amount-change and duplicate cases similarly distinguish known from unknown history. This is a small diagnostic experiment, not a statistically significant benchmark. Latency values are local wall-clock timings and are not equivalent to Groq latency. Mock calls have no token or monetary API cost; live provider costs were not measured.

The evaluation container ran Python 3.13.5, pytest 9.0.2, pandas 2.2.3, and python-dotenv 1.2.2. Two additional tests verify month-end date projection, including leap-year February, and guard against a false renewal-day shift for January 31 to February 28. It did not have Python 3.11, `langgraph`, `streamlit`, or `groq`; a pip dry-run failed because DNS/network access was unavailable. Therefore the core Python/SQLite tests and scenario harness ran, but the actual compiled graph, Streamlit UI launch, and live Groq request remain unverified in this environment. ## 8. Limitations and future work

Merchant normalization is based on a small alias dictionary and should be expanded cautiously. The renewal-day heuristic compares calendar day-of-month and may need more sophisticated month-end handling. The supplied CSVs do not contain explicit billing interval metadata; the register uses a monthly default for known merchants. Upcoming-renewal dates therefore require user confirmation and should not be treated as authoritative provider schedules. The application does not yet include a fully automated calendar-based renewal projection or a production-grade file upload store. Live Groq behavior depends on account model availability and credentials. The current environment did not permit frontend or graph dependency installation. These are explicit limitations rather than simulated successes.

The amount comparison deliberately retains the original register amount until the user confirms a correction. A temporary observed amount does not silently overwrite the approved baseline. The renewal projection is advanced from the earliest charge for each merchant in a cycle; later duplicate rows do not move the projected date. Each projection is written as a new register version. Renewal-day anomaly detection compares the current billing day with the prior cycle's billing day and flags shifts larger than three days. It is a heuristic, not provider-confirmed evidence.

## 11. Performance and reproducibility interpretation

The scenario runner measures wall-clock duration for each check. Its mean includes process startup for the cold-restart test, so it should not be compared directly with the sub-millisecond mock decision timings. The paired ablation file records six mock calls in total (three memory-on and three memory-off calls). The mean mock decision latency is a local timing observation only; it is not a network latency estimate. The mock provider exposes no token counts and incurs no Groq API usage. A live provider's token usage and monetary cost must be measured from the actual provider response/account usage if a live run is performed.

The ten scenario checks are integration-style deterministic exercises. The unit tests separately check lower-level behavior, including repeated ingestion, repeated decisions, repeated evidence, repeated approved corrections, and draft idempotency. The test suite's passing status does not establish the Streamlit UI or LangGraph runtime because those optional packages were unavailable in the runner. The correct reproducibility claim is therefore: core Python/SQLite logic passed its tests; the scenario harness passed its ten checks; paired mock ablation ran; frontend/graph/provider integration remains pending installation and direct execution.

## 12. Operational considerations

The application should be run locally with a database path writable only by the intended user. The user ID is a logical isolation key, not authentication; a shared machine requires operating-system account separation and appropriate file permissions. CSV uploads may contain sensitive financial descriptions, so uploaded statements and SQLite files should not be committed to source control or shared unintentionally. `.env` must remain private. The example configuration contains no credentials. Register exports are plain-text snapshots and should be handled with the same care as the source statements.

For a production deployment, the next engineering priorities would be authenticated user identity, encrypted-at-rest storage, stronger merchant identity resolution, explicit currency handling in rollups, provider-confirmed billing interval/renewal data, and a formal migration/versioning strategy. These enhancements are outside the demonstrated offline assignment scope and are not claimed as implemented.
